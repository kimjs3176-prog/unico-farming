# 스타일화된 게임 캐릭터·에셋

원본: [droppedoutofcontext/claude-3d-character-skill](https://github.com/droppedoutofcontext/claude-3d-character-skill) `skills/stylized-character` (MIT, © 2026 Ivan Vasilev, `LICENSE`). 러시아어 원문을 한국어로 옮기고 유니코 팜에 맞게 다듬었다. `scripts/` 는 원본 그대로.

콘셉트, 스케치, 생성한 그림을 보고 캐릭터·동물·마스코트·소품을 만드는 방법론이다. 원작자가 three.js 협동 게임의 스타일화된 캐릭터로 검증했다. 모델은 리뷰 다섯 바퀴 만에 콘셉트에 맞췄고, 움직임과 물리는 측정값과 콘티로 다듬었다.

목표는 하나다: **사용자는 취향만 고치고, 결함은 찾지 않게 한다.** 아래 모든 것은 이것 때문이다. 어떤 단계가 사용자보다 먼저 결함을 잡지 못한다면 건너뛰어도 된다.

## 유니코 팜에서 쓸 때 (먼저 읽기)

- **캐릭터는 Blender 로 만들지 않는다** (사용자 결정, `unico-farm-assets` 스킬). 주민 동물은 `scripts/lib/species_shapes.mjs`, 유니코는 `src/game/unico_mesh.js` 에서 **SDF + 스무스 유니온 → Surface Nets** 로 이음새 없는 한 덩어리 메시를 만들고 `npm run models:unico` 로 굽는다. 아래 "모델은 어디서" 표의 Blender 스크립트 경로 대신 **SDF 경로**를 쓴다: `references/unico-chibi-body.md`.
- Blender 스크립트 경로(`references/blender-modeling.md`, `scripts/blender_kit.py`)는 **소품·환경 에셋**에만 쓴다 (`blender/build_environment.py` 와 같은 자리).
- image-to-3D 결과는 캐릭터 런타임 모델로 넣지 않는다. 비율·실루엣을 재는 참고 자료로만 쓰고, 쓰려면 사용자에게 먼저 묻는다.
- 계약서(1단계 참고)의 기준 문서는 이미 있다: **`docs/CHARACTERS.md`** (아트 바이블: 캐스트, 규칙 12개, 팔레트, 리그, 움직임 표, 64px 실루엣 시험, 굽기와 검사). 새 계약서를 따로 만들지 말고 여기에 새 종·바뀐 수치를 더한다.
- 미리보기는 Blender 렌더 대신 `unico_preview.html?species=…&view=front|side|back|three|top` 을 Playwright 로 캡처한다 (GPU 없는 컨테이너는 swiftshader 옵션 — `unico-farm-assets` 스킬).
- 2차 동작(귀·꼬리 스프링)은 이미 `src/game/unico.js` `_speciesSecondary()` 에 있다. `scripts/motion_kit.js` 는 바꿔 끼우지 말고 규칙(고정 단계, 받침 기준 감쇠, 부드러운 한계, 공진 점검)을 대조하는 참고로 쓴다.
- 검사: `node --test tests/species.test.js tests/unc2.test.js tests/gait.test.js`, 그다음 `npm test`.

## 필요한 것

- **만드는 쪽**: 파일과 터미널을 쓰는 에이전트 (Claude Code).
- **리뷰어**: 그림을 보는 모델이면서 **별도 컨텍스트에서 일하는 것**. 이건 필수다. 만드는 쪽은 렌더에서 결과가 아니라 의도를 본다. 리뷰어는 콘셉트, 렌더, 계약서, `assets/reviewer-prompts.md` 의 요청문만 받고 수정 이력은 받지 않으며 파일을 고치지 않는다. 방법:
  - 같은 모델의 깨끗한 컨텍스트 서브에이전트 — 이것으로 충분하고 설치할 것이 없다;
  - MCP 로 연결한 다른 계열 모델 — 중요한 관문에 권장: 맹점이 다르다.
- **장면**: 에셋이 실제로 놓이는 페이지나 엔진. `scripts/` 의 도우미는 three.js 기준이다. 다른 엔진에는 세 가지가 필요하다: 콘셉트 각도의 렌더, 게임 크기 스냅샷, 프레임별 변형 측정.
- (일반 프로젝트) **Blender** 4.x 헤드리스(`blender -b -P script.py`) 또는 MCP. 복잡한 형태는 image-to-3D 서비스(Tripo3D, TRELLIS 등).

## 과정을 얼마나 할까

| 에셋 | 할 일 |
|---|---|
| 움직이지 않는 소품 (무기, 소도구, 탈것) | 짧은 계약서 → 모델 → 조립 → 형태 리뷰. 리그와 움직임은 건너뛴다. |
| 조연 캐릭터, NPC (마을 주민) | 짧은 계약서 (비율, 구성, 팔레트), 블록아웃은 안 보여 줘도 됨, 움직임은 아래 표의 기성 기법 |
| 주인공, 플레이어가 몇 시간씩 보는 것 (유니코) | 모든 단계 |

"짧게"는 계약서 파일 10~15줄이지 전체 템플릿이 아니다.

## 리뷰어와의 반복

이 방법론의 핵심이고, 나머지는 이것을 돕는다.

1. 만드는 쪽이 콘셉트와 같은 각도로 렌더를 찍는다 (움직임이면 콘티와 측정값).
2. 리뷰어가 비교해 **MUST**(막는 문제)와 **SHOULD**(취향) 목록으로 답한다. 항목마다 숫자가 있다: 키 대비 비율, 각도, 이동량.
3. 만드는 쪽이 MUST 를 숫자 변경으로 반영하고 다시 굽는다.
4. MUST 가 남아 있는 동안 반복한다. SHOULD 는 적어 두었다가 사용자에게 제안하고, 끝없이 다듬지 않는다.

보통 3~6바퀴면 된다. 6바퀴가 지나도 MUST 가 끝나지 않거나, 2~3바퀴 동안 실루엣이 콘셉트에 가까워지지 않으면 문제는 숫자가 아니라 접근법이다: 모델 경로를 바꾸거나(아래) 계약서로 돌아간다.

리뷰어가 싼 기법으로 충분한 곳에 새 시스템을 제안하면 싼 쪽을 고르고 이유를 설명한다.

## 모델은 어디서

0단계에서 계약서를 보고 정한다:

| 에셋 | 경로 |
|---|---|
| 유니코 팜 캐릭터 (주민 동물, 유니코) | **SDF 코드** (`references/unico-chibi-body.md`). 모든 수정은 숫자이고 한 명령으로 다시 굽는다. 스킨 가중치는 관절 경계 폭(SIGMA)으로 정해진다. |
| 큰 형태가 적은 것 (~10–15개까지): 두건, 망토, 캡슐, 모자, 단순한 팔다리, 손에 든 물건 | **Blender 스크립트** (`references/blender-modeling.md`). 모든 수정은 숫자이고 한 명령으로 다시 만든다. 변형 가중치도 스크립트에서 굽는다. |
| 부품이 많거나 실루엣·얼굴이 복잡한 것: 사실적인 동물, 알아볼 수 있는 이목구비, 기계, 여러 겹 옷 | **image-to-3D** 를 콘셉트 시트로 돌린 뒤 Blender 에서 정리: 계약서대로 크기와 축, 움직이는 부분 분리, 재질 슬롯, 예산에 맞춘 데시메이트, 가중치. 이것은 기초이지 리토폴로지가 아니다. (유니코 팜 캐릭터에는 쓰지 않음 — 위 참고) |

스크립트는 레퍼런스를 보고 복잡한 형태를 만들지 못한다: 알아볼 만한 기본 도형은 모으지만 콘셉트 속 캐릭터는 아니고, 리뷰를 몇 바퀴 돌아도 고쳐지지 않는다. 유니코 팜이 이 한계를 넘는 방법은 SDF 스무스 유니온이다: 도형을 녹여 붙이므로 이음새 없는 몸이 나온다.

## 단계

각 단계의 자세한 내용은 `references/` 에 있다. 지금 단계의 관문을 통과하기 전에는 다음 단계를 시작하지 않는다.

### 0. 계약서

`references/reference-analysis.md`, 전체 템플릿은 `assets/acceptance-checklist.md`. 일반 프로젝트는 `docs/characters/<이름>-contract.md`, **유니코 팜은 `docs/CHARACTERS.md` 의 해당 절**:

- **레퍼런스**: 원본 콘셉트가 생성한 시트보다 우선한다. 각 뷰를 지면과 단단한 기준점으로 정규화하고, 어긋나는 점은 다수결로 정한다. 각도가 하나뿐이면 리뷰어에게 정사영 시트를 요청한다(요청문 1).
- **비율**: 키 대비 비율과 허용 오차.
- **눈에 띄는 형태마다 구성**: 한 표면인지 별도 부품인지, 무엇이 무엇 아래에 있는지, 어디에 끼워 넣는지. 흔한 실수: 두건 끝을 별도 객체로 만들었는데 사실 같은 천의 주름.
- **팔레트**: 재질(슬롯) 이름별로.
- 캐릭터는 **반응 지도**: 무엇이 단단하고, 무엇이 통째로 흔들리고, 무엇이 대롱거리고, 무엇이 매달리고, 무엇이 손에 있는지, 그리고 그 캐릭터를 알아보게 하는 **결정적인 움직임 하나**.
- **예산**: 기본은 같은 장면의 지금 주인공보다 비싸지 않게. 주인공이 없으면 기기와 화면 속 캐릭터 수를 묻는다. (유니코 팜: `docs/CHARACTERS.md` §8 의 bin 용량 예산, `unico-perf-budget` 스킬)
- **모델 경로**: 위 표대로.

관문: 리뷰어가 콘셉트를 맞게 읽었다고 확인한다(요청문 2). 사용자에게는 논쟁이 되는 곳이 실루엣을 바꿀 때만 질문 하나를 한다.

### 1. 움직이는 블록아웃

큰 덩어리를 기본 도형으로, 실제 리그 위에서, 실제 장면에서: 달리고, 뛰고, 돈다. 플레이어가 보는 크기로, 실제 배경에서 본다. 사용자에게 한 번 보여 준다: "방향과 실루엣이 맞나요?" 틀리기 가장 싼 순간이다.

### 2. 모델

SDF 코드(유니코 팜), 스크립트, 또는 image-to-3D 정리(`references/blender-modeling.md`). 움직이는 부분은 관절에 중심을 둔 별도 객체로; 한 덩어리 메시라면 가려진 이음새에서 자르거나 스키닝한다(Rigify, 자동 가중치, Mixamo; 유니코 팜은 SIGMA 경계 가중치). 재질 이름은 칠하기 슬롯이고, 변형 가중치는 정점 속성으로 내보내며 [0, 1] 로 자른다. 네 방향 미리보기를 콘셉트 옆에 같은 각도로 놓는다.

관문: 리뷰어와의 반복(요청문 3)이 MUST 없이 끝났고, 비율이 허용 오차 안이며, 가중치가 GLB/bin 까지 갔고 NaN 이 없다.

### 3. 엔진 조립

`references/engine-integration.md`. 재질 이름으로 칠하고, 변형은 모든 패스(기본, 외곽선, 그림자)에 넣는다. 필수 가중치가 없으면 0 으로 채우지 말고 알기 쉬운 오류로 로드를 멈춘다.

검사 시트: 한 바퀴 각도, 위에서, 얼굴 3/4, **실제 배경 위 게임 크기 스냅샷**, **극단을 동시에** (고개 돌리기, 흔들림, 점프). 변형을 눈에 띄는 각도로 강제로 걸고 천이 휘는지 눈으로 확인한다.

관문: 시트에 결함 0, 프레임 예산 준수.

### 4. 움직임

`references/motion-recipes.md`, 코드는 `scripts/motion_kit.js`. 요소마다 읽히는 가장 싼 기법을 쓴다:

| 요소 | 기법 |
|---|---|
| 두건, 모자, 자루, 치마 통째로 | 숙임·기울기·비틀기 스프링 → 구운 가중치로 셰이더에서 회전 |
| 뾰족한 끝, 꼬리, 귀, 땋은 머리 | 두 마디 Verlet 사슬, 120 Hz, 부드러운 한계 |
| 털, 머리카락 다발 | 공통 스프링에 위상을 다르게 한 큰 다발 몇 개 |
| 매달린 물건 | 원뿔과 몸 평면이 있는 진자 |
| 망토, 옷자락 | 셰이더 굽힘: 끌림과 비틀림 |
| 안경, 버클, 갑옷 | 뼈에 단단히, 변형 없음 |

"촉감 있게", "달리기가 기분 좋게" 같은 느낌 요청은 측정값과 목표로 바꾼다. 파라미터는 진동수와 감쇠에서 끌어낸다 (`k = (2πf)²`, ζ 0.4–0.6). 이미 수정 바퀴를 치르게 했던 물리 규칙은 `references/motion-recipes.md` 에 있다.

관문: `references/verification.md` 의 시나리오가 목표 범위 안, 30/60/120 FPS 와 멈칫한 뒤에도 안정. 리뷰어가 콘티와 측정값을 본다(요청문 4).

### 5. 보여 주기

`references/verification.md`. 측정은 입력 파라미터가 아니라 **실제 정점 변형**에서 한다. 콘티는 부드러움을 보여 주지 못한다: 마지막 판단은 실제 재생이고, 영상을 보여 줄 수 없으면 그렇다고 말한다.

보고에는: 무엇이 바뀌었는지, 사용자 불만별 "전 → 후" 숫자, 무엇을 검사했고 무엇은 손으로만 확인할 수 있는지, 리뷰어가 뭐라고 했는지, 무엇을 취향으로 남겼는지.

## 사용자가 불만을 말할 때

불만을 측정 가능한 증상으로 바꾸고(`references/pitfalls.md`), 프레임별 추적을 찍고, 고치고, 다시 재고, 숫자를 보여 준다. "뻣뻣해" — 이동량과 한계에 닿는 비율; "덜컥거려" — 프레임당 방향 변화; "물리답지 않아" — 매달린 것이 한계에 붙어 있음; "레퍼런스랑 달라" — 콘셉트 옆의 같은 각도와 리뷰(요청문 3); "몸이 어색해"(2~3등신) — `references/unico-chibi-body.md` 의 비율·이음새 점검. 다듬기는 시간을 정해 둔다.

## 실무
