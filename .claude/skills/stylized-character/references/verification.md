# 보여 주기 전 검사

원칙: 사용자는 측정, 콘티, 리뷰어를 통과한 것만 본다.

> 유니코 팜: 스냅샷은 `unico_preview.html?species=…&view=…&pose=…` 또는 게임 서버 + `window.game` API 를 Playwright 로 캡처한다 (`unico-farm-assets` 스킬 "검증"). 64px 실루엣 시험과 굽기 검사는 `docs/CHARACTERS.md` §7–§8, 프레임 예산은 `unico-perf-budget` 스킬.

## 장면에 필요한 것

어떤 엔진에서든 훅 세 개:
- **스냅샷**: 고른 각도나 게임 프레임을 PNG 로 (웹에서는 `canvas.toBlob` 과 `build/review/` 에 파일을 쓰는 `scripts/capture_server.py`; Playwright 를 쓰면 `page.screenshot` 으로 충분);
- **시뮬레이션 단계**: 실제 시간을 기다리지 않고 정한 `dt` 와 입력(키, 몸짓)으로 n 프레임 돌리기;
- **위치**: 변형 뒤 정점이나 노드의 세계 위치.

아래 시나리오는 모두 이 세 훅으로 만든다. three.js 의 프레임 시간은 `scripts/page-helpers/dev-perf.js` 가 잰다.

## 입력이 아닌 실제 변형

측정은 결과를 잰다: 셰이더 뒤 정점이 어디 있는지, 진자가 세계에서 어디 매달려 있는지, 발이 어디 서 있는지. 셰이더 굽힘은 **실제 정점과 그 정점의 가중치로** CPU 에서 공식을 되풀이한다(`motion_kit.js` 의 `clothBendCPU()`). 평균 가중치를 쓴 고리 중심은 안 된다: 바로 눈에 보이는 것을 뭉갠다.

덜컥거림은 **방향으로** 센다: 이웃 프레임 사이 끝 방향의 각도. 각도 크기의 차이는 안 된다: +30° 에서 −30° 로 넘어가도 "변화 0"이 된다.

측정 전에 **강제 굽힘**: 변형을 30° 로 걸고 그림을 본다. 그리고 가중치가 아예 기하까지 갔는지 확인한다: 0 이 아니고, NaN 이 없고, 키에 따라 합리적으로 분포.

## 시나리오

| 시나리오 | 볼 것 |
|---|---|
| 제자리 둘러보기 | 통째 흔들림, 끝 이동량 |
| 캐릭터의 몸짓들 | 한계, 팔과 몸 충돌 |
| 제자리 돌기 | 옷자락 비틀림, 매달린 것이 바깥으로 |
| 제자리 출발 | 매달린 것의 덜컥, 숙임 |
| 가속 뒤 달리기와 전력질주 | 한계, 이동량, 발 미끄러짐, 걸음 진동수 |
| 멈춤, 70–90 프레임 | 넘침과 가라앉음 |
| 원 그리며 달리기 | 회전에서 옷자락이 나가는 것 |
| 제자리·도움닫기 점프 | 프레임당 덜컥, 한계, 착지 |
| 모든 것 뒤 쉬기, 90 프레임 | 모두 돌아옴, 떨림 없음 |
| 계약서의 충돌 쌍 | 머리, 몸, 옷을 뚫고 지나가는 것 없음 |

## 공통 목표

캐릭터와 상관없는 목표. 흔들림, 끝 이동량, 매달린 것의 범위는 원하는 진동수와 진폭으로 계약서에서 정한다(`references/motion-recipes.md`).

| 측정 | 목표 |
|---|---|
| 요소의 프레임당 최대 방향 변화 | 60 FPS 에서 8° 미만; 15–20° 부터 덜컥임이 보임 |
| 평지 달리기에서 딱딱한 한계 | 프레임의 5% 미만; 출발 때는 20% 까지 허용 |
| 멈춤이나 착지 뒤 가라앉음 | 1초 미만, 넘침 두 번 이하 |
| 쉬기 | 1.5초 뒤 흔들림 3° 미만 |
| 디딘 발 | 거의 정지: 미끄러짐이 달리기 속도보다 훨씬 작음 |
| NaN, 콘솔 오류 | 0 |

## 안정성

달리기와 점프를 30, 60, 120 FPS 로 돌린다. 따로 — 멈칫(달리는 중 한 프레임 200ms)과 순간 이동(5m 옮김). 기대: 폭발과 NaN 없음, 멈칫 뒤 빨리 감아 따라잡기 없음, 순간 이동 뒤 휘청임 없음.

## 게임 크기와 극단

- 플레이어가 캐릭터를 보는 크기(자기 게임에서 잰다)로, 실제 배경과 빛에서 찍는다. 거기서 실루엣이 읽히는지, 디테일이 잡음이 되지 않는지 보인다.
- 극단을 동시에: 급한 고개 돌리기, 흔들림, 점프; 매달린 것과 함께 달리다 돌기. 이음새와 얼굴 구멍 속 다른 것은 이렇게만 드러난다.

## 성능

대상 기기에서 전체 구성으로 프레임을 잰다: 게임에 나올 만큼의 캐릭터 수, 모든 패스. 먼저 지금 주인공으로 기준, 있으면. 그다음 같은 장면에서 새것으로. 삼각형만이 아니라 프레임 시간과 그리기 호출 수를 본다. 안 맞으면 먼저 매끈함, 분할, 부품 수를 줄이고, 그다음 패스.

## 콘티

콘티는 포즈를 보여 주지만 부드러움과 반응성은 보여 주지 못한다. 가능하면 짧은 영상을 찍는다. 안 되면 사용자에게 부드러움은 숫자로만 확인했다고 말한다.

- 4×2 격자(점프는 4×3), 시간은 왼쪽에서 오른쪽, 위에서 아래.
- 카메라는 캐릭터를 따라가고, **높이도** 따라가며, 다른 캐릭터를 뚫고 지나가지 않는다.
- 각도: 옆(끝, 넘침), 뒤 3/4(걸음, 옷자락), 앞(얼굴, 매달린 것), 뒤 위.
- 리뷰어에게는 1024px 이하로 줄인 사본을 준다.

## 프레임별 추적

무언가 "덜컥거리거나" "물리답지 않을" 때는 먼저 추적을 찍는다: 지면 상태, 속도, 받침 가속도, 마디 각도, 필터와 진자 상태. 원인은 거의 항상 갑자기 튀는 열에서 보인다.

## 리뷰

템플릿은 `assets/reviewer-prompts.md`. "전 → 후" 숫자와 콘티 경로를 주고, 수정 이야기는 하지 않는다. 구체적인 숫자로 5–10줄 답을 요청한다. 리뷰어가 뭐라고 했는지 사용자에게 전한다.

게시한 뒤에는 호스팅에서 게시된 것을 다시 읽어 로컬 파일과 비교한다.
